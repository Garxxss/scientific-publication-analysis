# Технологический стек

Предлагаемый стек для команды из двух человек и учебного MVP. Совместимые версии закрепляются после проверки в репозитории. Готовая конфигурация и её производительность пока не заявляются.

| Компонент | Технология | Назначение |
|---|---|---|
| Веб-интерфейс | React + TypeScript + Vite | Библиотека публикаций, загрузка PDF, постановка вопроса, просмотр ответа и цитат. |
| Серверный API | Python + FastAPI + Pydantic | Приём запросов, проверка схем данных, операции с публикациями, вопросами и заданиями. |
| Данные и поиск по фрагментам | PostgreSQL + pgvector | Хранение метаданных, страниц, фрагментов, цитат, векторов, заданий и журнала действий. |
| Доступ к данным и миграции | SQLAlchemy + Alembic | Модели данных, транзакции и воспроизводимые изменения схемы PostgreSQL. |
| Извлечение текста | pypdf | Постраничное извлечение текста из PDF с текстовым слоем. |
| Просмотр источника | PDF.js | Отображение исходного PDF в браузере и переход на страницу цитаты. |
| Длительные задания | Таблица jobs в PostgreSQL + отдельный Python worker | Выполнение обработки PDF и анализа с сохранённым статусом и проектируемым восстановлением после сбоя. |
| Доступ к моделям | Один серверный адаптер LLM: совместимый HTTP API или Ollama | Генерация ответа и запросы эмбеддингов через согласованный интерфейс приложения. |
| Управляемый ход анализа | Простая машина состояний на Python с журналом переходов в PostgreSQL | Ограниченная цепочка поиска, сбора доказательств, генерации и проверки ссылок. |
| Внешний поиск | arXiv API | Поиск публикаций, получение метаданных и импорт выбранных материалов. |
| Запуск и хранение файлов | Docker Compose | Совместный запуск API, worker и PostgreSQL с постоянными volumes. |
| Проверки и CI | pytest + Playwright Python + GitHub Actions | Проверка серверной логики и полного пути пользователя от PDF до перехода к цитате. |

## Обоснования и ограничения

### Веб-интерфейс

Один клиент с готовым шаблоном react-ts. Для учебного сервиса не требуется отдельная серверная платформа фронтенда.

После сборки статические файлы отдаёт FastAPI. Совместимые версии Node.js и пакетов фиксируются в окружении и lock-файле; тег latest в развёртывании не используется.

[Официальная документация](https://vite.dev/guide/)

### Серверный API

Единый Python-код для API и обработки литературы; Pydantic задаёт явные контракты входных и выходных данных.

Длительный анализ выполняется отдельным worker. FastAPI BackgroundTasks не используется как очередь с восстановлением после перезапуска.

[Официальная документация](https://fastapi.tiangolo.com/tutorial/body/)

### Данные и поиск по фрагментам

Одна база обслуживает связанные данные и векторный поиск; отдельная векторная СУБД на этапе MVP не требуется.

Для малого контрольного корпуса сначала используется точный поиск; приблизительный индекс вводится после измерения необходимости. Для эмбеддингов фиксируются модель, ревизия и размерность; изменение модели требует переиндексации.

[Официальная документация](https://github.com/pgvector/pgvector)

### Доступ к данным и миграции

SQLAlchemy используется в API и worker; Alembic хранит историю схемы вместе с кодом.

Для первой версии достаточно обычных синхронных сессий в синхронных обработчиках. Миграции проверяются перед применением, а изменение индексов и векторной размерности описывается явно.

[Официальная документация](https://alembic.sqlalchemy.org/en/latest/)

### Извлечение текста

Постраничный API позволяет сохранять соответствие фрагмента исходному документу и номеру страницы.

Сканы, надёжный разбор таблиц и формул не входят в возможности этого минимального конвейера. Для пустого текста возвращается понятный статус. Ввод ограничивается по размеру и ресурсам обработки; исходный PDF хранится в постоянном файловом volume.

[Официальная документация](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

### Просмотр источника

Одна библиотека просмотра позволяет проверять сгенерированный ответ по исходной публикации.

В MVP гарантируемым результатом реализации должен стать переход на проверенный номер страницы, а не автоматическая точная подсветка произвольного извлечённого текста. Числовая нумерация страниц файла отделяется от напечатанного номера страницы.

[Официальная документация](https://mozilla.github.io/pdf.js/)

### Длительные задания

Используется уже выбранная база; для одной небольшой очереди не добавляются Redis и отдельный брокер. PostgreSQL документирует SKIP LOCKED для нескольких потребителей таблицы очереди.

Нужно реализовать короткую транзакцию захвата задания, lease/heartbeat, ограниченные повторы и идемпотентность шагов. Внешний вызов LLM не держит открытую блокировку строки. SKIP LOCKED сам по себе не обеспечивает восстановление или выполнение ровно один раз; это проверяется остановкой worker и повторным запуском.

[Официальная документация](https://www.postgresql.org/docs/current/sql-select.html)

### Доступ к моделям

Остальной код не зависит от одного провайдера. Генеративная модель и модель эмбеддингов выбираются раздельно по результатам пилота.

Совместимость Ollama охватывает часть API, поэтому отдельно проверяются нужные методы и схемы ответов. Фиксируются model name, revision, quantization, embedding dimension, параметры генерации и тайм-ауты. Локальное название модели не доказывает, что весь конвейер не передаёт данные наружу: проверяются фактические адреса сервисов и выбранные модели.

[Официальная документация](https://docs.ollama.com/api/openai-compatibility)

### Управляемый ход анализа

Для первой версии явная таблица переходов проще отдельного агентного фреймворка. Состояния задаются перечислением; результаты и переходы сохраняются в базе. Это проектное решение, а не готовая возможность Enum.

Есть предел шагов, остановка пользователем и состояния ошибки. Проверка ссылок подтверждает существование фрагмента и страницы, но не истинность ответа. LangGraph рассматривается позже, если появятся сложные ветвления и будет обоснована польза его механизмов исполнения.

[Официальная документация](https://docs.python.org/3/library/enum.html)

### Внешний поиск

Один документированный источник сокращает число интеграций, форматов и сценариев ошибок в MVP.

Используются идентификаторы и версии arXiv, пагинация, кэш и соблюдение правил частоты запросов. Учитываются лицензия конкретной публикации и ограниченность предметного охвата; наличие метаданных не заменяет проверку доступности полного текста.

[Официальная документация](https://info.arxiv.org/help/api/user-manual.html)

### Запуск и хранение файлов

API и worker собираются из одного кода, а конфигурация сервисов хранится в одном Compose-файле. Для учебного развёртывания не требуется Kubernetes.

Собранный веб-клиент включается в образ API. Версии образов фиксируются; volume базы и volume PDF сохраняются между перезапусками. Резервное копирование и проверка восстановления планируются отдельно: наличие volume не является резервной копией.

[Официальная документация](https://docs.docker.com/compose/)

### Проверки и CI

Backend и браузерные сценарии используют Python и pytest; официальный пример Playwright показывает запуск через GitHub Actions.

В CI применяется управляемая заглушка LLM, проверяются соответствие цитат страницам, ошибки обработки и восстановление jobs. Качество настоящей модели оценивается отдельно на фиксированном корпусе с записанной конфигурацией. Браузер Playwright и зависимости закрепляются совместимыми версиями.

[Официальная документация](https://playwright.dev/python/docs/ci)

## Стартовые модели для пилота

- Генерация: [Qwen3-8B](https://huggingface.co/Qwen/Qwen3-8B) через Ollama.
- Эмбеддинги: [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3), dense, размерность 1024.

Фиксируются идентификатор, ревизия, квантование, параметры генерации и размер контекста. Память, время и качество измеряются на нашем корпусе. При замене модели эмбеддингов корпус переиндексируется.
